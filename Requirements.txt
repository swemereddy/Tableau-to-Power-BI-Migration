2. Executive Summary
This Requirements Document defines the business and technical requirements for migrating the organization's Tableau reporting portfolio to Microsoft Power BI. The program covers assessment, redesign, rebuild, validation, and cutover of the in-scope reports, and establishes the technical foundation (licensing, data connectivity, security, and governance) required to operate the reporting estate on Power BI going forward.
3. Project Scope
3.1 In Scope
•	Report Migration Volume: Migration of 80 Tableau reports/dashboards (including underlying workbooks, worksheets, and data sources) to Power BI.
•	Assessment & Inventory: Full inventory and complexity assessment of all 80 Tableau workbooks (data sources, calculated fields, LOD expressions, parameters, filters, actions, extracts).
•	Data Model Rebuild: Recreation of semantic/data models in Power BI (Power Query transformations, relationships, DAX measures) equivalent to existing Tableau data models.
•	Visualization Rebuild: Rebuilding dashboards, visuals, interactivity (filters, drill-through, tooltips, bookmarks) to match or improve on existing Tableau functionality.
•	Data Connectivity: Re-establishing connections to all source systems currently feeding Tableau (databases, cloud warehouses, files, APIs) within Power BI.
•	Security Model Migration: Migration of row-level security (RLS), user/group access, and folder/project permissions from Tableau Server to Power BI workspaces.
•	Testing & Validation: Data validation (source-to-report reconciliation), visual/functional parity testing, and formal UAT sign-off for each report.
•	Deployment & Publishing: Publishing to Power BI Service, workspace/app configuration, and scheduled refresh setup.
•	Training & Documentation: End-user and administrator training, and updated technical/user documentation.
•	Hypercare & Cutover: Post-go-live support period and decommissioning plan for legacy Tableau content.
3.2 Out of Scope
•	Migration of Tableau Prep flows unless explicitly called out as a separate workstream.
•	New report development beyond functional parity, unless approved via change request.
•	Migration of ad-hoc, personal, or unpublished/sandbox Tableau workbooks not in the agreed inventory of 80.
•	Source system remediation or data warehouse re-architecture (assumed to be stable and available).
•	Procurement of source-system licenses (only Power BI/Microsoft licensing is in scope).
•	Decommissioning of Tableau Server infrastructure itself (only the reporting content), unless separately agreed.

4. Objectives & Success Criteria
1.	Achieve 100% functional and visual parity (or documented, approved deviation) for all 80 reports.
2.	Ensure 100% data accuracy between legacy Tableau output and new Power BI output during validation.
3.	Consolidate BI licensing cost by retiring Tableau licenses post-migration.
4.	Standardize on Microsoft Power BI as the enterprise reporting/analytics platform, aligned to the existing Microsoft 365/Azure ecosystem.
5.	Preserve or improve existing report refresh schedules and performance SLAs.
6.	Ensure zero unauthorized access change - security parity (or stricter) versus the current Tableau permission model.
7.	Complete migration with minimal disruption to business users (defined cutover windows, parallel run period).

6. Target State (Power BI Environment)
•	Power BI Service tenant configured with appropriate capacity (Power BI Premium / Fabric capacity or Premium Per User, based on volume and refresh needs).
•	Workspace structure aligned to business units/domains, mirroring or improving on the current Tableau project structure.
•	Standardized semantic models (shared datasets) to promote reuse across reports and reduce duplication.
•	Power BI Apps used for end-user distribution in place of Tableau Server projects.
•	Gateway infrastructure (On-premises Data Gateway) established for on-prem source connectivity.
•	Row-level security implemented natively via Power BI RLS roles.
•	Naming conventions, folder structure, and documentation standards defined and applied consistently.

 10. Technical Requirements & Technicalities
This section consolidates all technical workstreams and prerequisites needed to execute the migration end-to-end.
10.1 Licensing & Capacity
•	Power BI Pro or Premium Per User (PPU) licenses for all report developers and authors.
•	Power BI Premium capacity (P-SKU) or Microsoft Fabric capacity (F-SKU) sized based on total dataset volume, concurrent users, and refresh frequency across all 80 reports.
•	Microsoft 365 / Entra ID (Azure AD) tenant with appropriate licensing for SSO and group-based access.
•	Cost comparison and license reconciliation against existing Tableau Creator/Explorer/Viewer licensing to validate savings.
10.2 Infrastructure & Connectivity
•	On-premises Data Gateway (Standard or Personal, per environment) installed and configured for any on-prem source connections (SQL Server, Oracle, file shares, etc.).
•	Network/firewall rules updated to permit gateway and Power BI Service connectivity to source systems.
•	Service accounts (with least-privilege access) provisioned for scheduled dataset refreshes.
•	Azure/cloud data source endpoints (Synapse, Snowflake, Redshift, BigQuery, etc.) validated for native Power BI connector support.
•	Capacity/workspace region alignment with data residency requirements.
10.3 Data Source & Connector Requirements
Tableau Source Type	Power BI Equivalent / Connector
Live connection (SQL Server, Oracle, Teradata, etc.)	DirectQuery or Import via native Power BI connector
Extract (.hyper)	Import mode dataset with scheduled refresh
Custom SQL query	Power Query (M) equivalent query or native SQL query step
Excel/CSV/flat files	Power Query file/folder connector, ideally moved to a shared location (SharePoint/OneDrive)
Cloud data warehouse (Snowflake, BigQuery, Redshift, Synapse)	Native Power BI connector or DirectQuery
Web Data Connector / API	Power Query Web connector or custom connector via M/Power Query SDK
Tableau Server published data source	Rebuilt as Power BI shared dataset / dataflow
10.4 Data Modeling & Transformation
•	Recreate Tableau data source joins/blends as Power BI relationships (star schema recommended where feasible).
•	Rebuild ETL/data prep logic (including Tableau Prep flows, if in scope) as Power Query (M) transformations or dataflows.
•	Convert LOD expressions (FIXED, INCLUDE, EXCLUDE) to equivalent DAX (CALCULATE, ALLEXCEPT, SUMMARIZE, etc.).
•	Convert Tableau table calculations (running total, quick table calc, rank) to DAX time-intelligence and window functions.
•	Rebuild Tableau parameters as Power BI What-if parameters or field parameters.
•	Rebuild Tableau Sets and Groups using DAX calculated tables/columns or Power BI groups.
•	Establish a shared/certified dataset strategy to avoid duplicate data models across related reports.
10.5 Visualization & Interactivity Rebuild
•	Map each Tableau chart type to its closest native Power BI visual, or a certified/custom visual from AppSource where no native equivalent exists.
•	Rebuild dashboard actions (filter, highlight, URL/navigation) using Power BI cross-filtering, drill-through pages, and bookmarks.
•	Recreate Tableau Stories using Power BI bookmarks and the Selection pane, or multi-page report navigation.
•	Apply consistent theming (JSON theme file) to match corporate branding previously defined in Tableau workbooks.
•	Validate tooltips, custom tooltips, and drill-through tooltip pages for parity.
10.6 Security & Governance
•	Implement static and/or dynamic Row-Level Security (RLS) roles in Power BI mapped from Tableau user filters/groups.
•	Map Tableau Server groups/roles to Entra ID (Azure AD) security groups for workspace and app access.
•	Define workspace roles (Admin, Member, Contributor, Viewer) per business unit, replicating Tableau project-level permissions.
•	Configure sensitivity labels (Microsoft Purview Information Protection) for data classification, if in use organization-wide.
•	Establish a Power BI tenant governance policy (workspace naming, certification/endorsement of datasets, sharing controls).
10.7 Performance & Optimization
•	Benchmark current Tableau extract/query performance to set target SLAs for Power BI.
•	Optimize data models (star schema, appropriate cardinality, disabled auto date/time) for DAX performance.
•	Use incremental refresh policies for large datasets to reduce refresh time and capacity load.
•	Apply query folding best practices in Power Query to push transformation logic to source where possible.
•	Use Performance Analyzer and DAX Studio/Tabular Editor to tune slow reports during testing.

 11. Migration Approach & Methodology
11.1 Phased Wave Approach
8.	Phase 0 - Discovery & Assessment: Inventory all 80 reports, score complexity (Low/Medium/High), identify quick wins and high-risk items.
9.	Phase 1 - Foundation Setup: Provision tenant, capacity, gateways, workspaces, security groups, and standards/templates.
10.	Phase 2 - Wave-Based Migration: Group reports into waves (e.g., 4-6 waves of ~15-20 reports) by business priority and complexity.
11.	Phase 3 - Build: Data model + report rebuild per wave, following design standards.
12.	Phase 4 - Validation: Data reconciliation and visual/functional parity testing per report.
13.	Phase 5 - UAT & Sign-off: Business user review and formal acceptance per report.
14.	Phase 6 - Cutover: Publish to production workspaces/apps, redirect users, run parallel period.
15.	Phase 7 - Hypercare & Decommission: Post-go-live support, then retire legacy Tableau content per sign-off.
11.2 Complexity-Based Effort Tiering
Complexity Tier	Characteristics	Indicative Effort
Low	Single data source, standard charts, no LOD/complex calcs	1-2 days/report
Medium	Multiple sources, some LOD expressions, filters/actions	3-5 days/report
High	Complex blends, heavy LOD/table calcs, custom SQL, many actions	6-10+ days/report

Refer to Section 10.1 (Licensing & Capacity) and 10.6 (Security & Governance). Additionally:

•	Data governance policies must define who can publish, certify, and share datasets/reports in production workspaces.
•	Access reviews should be conducted post-migration to confirm no over-provisioned access versus the legacy Tableau model.
15. Testing & Validation (UAT)
Test Type	Description
Data Validation	Row-level and aggregate reconciliation between Tableau source output and Power BI output
Functional Testing	Filters, parameters, drill-through, actions, and navigation behave as expected
Visual Parity Testing	Side-by-side visual comparison against legacy Tableau report
Performance Testing	Load time, refresh duration, and query response benchmarked against SLA
Security Testing	RLS validated per user/role to confirm correct data visibility
UAT	Business report owner reviews and formally signs off each migrated report
16. Training & Change Management
•	End-user training on Power BI navigation, filtering, export, and subscription features.
•	Power user/developer training on Power BI Desktop, DAX, and Power Query for the internal BI team.
•	Administrator training on workspace/capacity management, gateway administration, and monitoring.
•	Communication plan and cutover notices issued to all report consumers ahead of each wave go-live.
•	Quick-reference guides and recorded walkthroughs published for self-service support.
17. Cutover & Decommissioning
16.	Run a parallel period (recommended 2-4 weeks) where both Tableau and Power BI versions are available.
17.	Obtain formal business sign-off per report before disabling the Tableau version.
18.	Redirect scheduled subscriptions/alerts and embedded links to the new Power BI reports.
19.	Archive legacy Tableau workbooks and extracts per data retention policy.
20.	Decommission Tableau licenses/server access per the agreed retirement schedule.
18. Assumptions, Dependencies & Constraints
18.1 Assumptions
•	Source systems currently feeding Tableau remain stable and accessible throughout the project.
•	Business report owners are available for requirements walkthroughs and UAT within agreed timelines.
•	The count of 80 reports reflects unique, currently active, published Tableau content (excludes duplicates/drafts).
•	Power BI tenant and licensing procurement is completed prior to Phase 1.
18.2 Dependencies
•	Availability of Tableau Server/Desktop access for the migration team to inspect legacy workbook logic.
•	Timely provisioning of source system credentials/service accounts by IT/DBA teams.
•	Timely procurement of Power BI licenses and capacity by IT Procurement.
18.3 Constraints
•	Migration must not disrupt existing scheduled reporting/business decision cycles during transition.
•	Any custom Tableau visuals/extensions without a Power BI equivalent may require a custom visual or approved design deviation.
19. Risks & Mitigation
Risk	Impact	Mitigation
Complex LOD/table calculations do not translate cleanly to DAX	High	Early technical spike on high-complexity reports; engage DAX SMEs
Data discrepancies between source and target	High	Mandatory reconciliation testing before UAT for every report
Underestimated capacity/licensing needs	Medium	Capacity sizing exercise and pilot wave before full rollout
User adoption resistance	Medium	Early stakeholder engagement, training, and parallel run period
Missing/undocumented Tableau custom SQL logic	Medium	SME workshops and source code review during discovery phase
On-prem gateway connectivity issues	Medium	Early gateway setup and connectivity testing in Phase 1
